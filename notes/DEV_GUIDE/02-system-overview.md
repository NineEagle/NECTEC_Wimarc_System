# บทที่ 02 — ภาพรวมระบบทั้งหมด

> อ่าน 15 นาที

ระบบนี้ไม่ได้มีแค่ "เว็บ" ตัวเดียว แต่มี 5 ชิ้นส่วนทำงานพร้อมกันบนเซิร์ฟเวอร์เดียว
ถ้าเข้าใจภาพนี้ เวลามีปัญหาคุณจะรู้ทันทีว่าต้องไปดูที่ชิ้นไหน

## แผนภาพระบบ

```
  ┌──────────── ฝั่งเว็บ — งานของคุณอยู่ตรงนี้ ────────────────────────────────┐
  │                                                                           │
  │  เบราว์เซอร์  ──HTTPS──►  Apache  ──proxy──►  Next.js  ──rewrite──►  FastAPI  ──SQL──►  PostgreSQL 16
  │  ผู้ใช้ 30 สวน            :80/:443           :3000                :8000              (ข้อมูลทั้งหมด)
  │                        SSL + กันเส้นทาง      หน้าเว็บ            API 64 เส้นทาง          ▲
  │                          ของ PHP เดิม                                                   │
  │                                     └──── อยู่ใน Docker: แก้โค้ดแล้วต้อง rebuild ────┘   │
  └───────────────────────────────────────────────────────────────────────────────────────┼──┘
                                                                                          │
  ┌──── ฝั่งอุปกรณ์ — ไม่ต้องแตะ ────┐                                                      │
  │                                                                                       │
  │  ESP32 ในสวน  ──HTTP──►  PHP เดิม (legacy)  ──────── INSERT ลงตารางเซนเซอร์เดิม ───────┘
  │  60 บอร์ด               InsertdataW32_*.php
  └──────────────────────────────────────┘
```

จุดสำคัญ: **ข้อมูลจากอุปกรณ์เข้าทาง PHP เดิม ส่วนเว็บอ่านข้อมูลเดียวกันผ่าน FastAPI**
สองเส้นทางนี้แยกกันสิ้นเชิง เจอกันที่ฐานข้อมูลเท่านั้น

## ใครทำอะไร

| ชิ้นส่วน | ทำหน้าที่ | อยู่ที่ไหน | ต้องแก้บ่อยไหม |
|---|---|---|---|
| **Apache** | รับคำขอจากอินเทอร์เน็ต ทำ HTTPS ส่งต่อให้ Next.js และกันไม่ให้ path ของ PHP เดิมโดนส่งผิดที่ | `/etc/apache2/sites-available/wimarc-in-th.conf` | นาน ๆ ครั้ง |
| **Next.js** (frontend) | วาดหน้าเว็บทุกหน้า จัดการล็อกอินฝั่งผู้ใช้ และส่งต่อคำขอ `/backend/*` ไปให้ FastAPI | `app/`, `components/`, `services/` | **บ่อยที่สุด** |
| **FastAPI** (backend) | ตรวจสิทธิ์ อ่าน/เขียนฐานข้อมูล คำนวณค่า แล้วตอบเป็น JSON | `backend/app/main.py` | บ่อย |
| **PostgreSQL 16** | เก็บข้อมูลทั้งหมด ทั้งข้อมูลของเว็บและข้อมูลดิบจากเซนเซอร์ | รันบนเครื่องโดยตรง ไม่ได้อยู่ใน Docker | แทบไม่แตะเอง |
| **PHP เดิม** | รับข้อมูลจากบอร์ด ESP32 แล้วเขียนลงตารางเซนเซอร์ | `/var/www/wimarc/*.php` | ไม่ต้องแตะ |

## 3 ช่องทางเข้าถึงข้อมูล

ระบบเปิดทางให้เข้าถึงข้อมูล 3 ทาง แต่ละทางยืนยันตัวตนคนละแบบ

| ช่องทาง | ใคร → ใคร | ยืนยันตัวตนด้วย |
|---|---|---|
| **A** | ESP32 → Apache/PHP → PostgreSQL | ไม่มี (ตาม design ของอุปกรณ์สนาม) |
| **B** | เบราว์เซอร์ → Next.js → FastAPI → PostgreSQL | JWT ในหัวข้อ `Authorization: Bearer` |
| **C** | ระบบภายนอก → FastAPI | API key ในหัวข้อ `X-Api-Key` (ขึ้นต้นด้วย `wmk_`) |

คู่มือเล่มนี้พูดถึงช่องทาง B เป็นหลัก ช่องทาง C มีหน้าจัดการอยู่ที่ `/admin/api-keys`
และมีหน้าให้คนนอกขอคีย์เองที่ `/request-api` กับ `/portal`

## ทำไมถึงแยก frontend กับ backend

เพราะสองฝั่งมีหน้าที่คนละอย่าง:

- ฝั่งหน้าเว็บสนใจว่า "แสดงยังไงให้สวยและใช้ง่าย"
- ฝั่ง backend สนใจว่า "ข้อมูลถูกต้องไหม คนนี้มีสิทธิ์เห็นไหม"

**การตรวจสิทธิ์ต้องอยู่ฝั่ง backend เสมอ** เพราะโค้ดฝั่งหน้าเว็บถูกส่งไปรันในเครื่องผู้ใช้
ใครก็เปิดดูและแก้ได้ การซ่อนปุ่มในหน้าเว็บไม่ใช่การรักษาความปลอดภัย เป็นแค่ความสะดวกสายตา

## เว็บเรียก API อย่างไร

เวลาเว็บเรียก API มันไม่ได้ยิงไปที่พอร์ต 8000 ตรง ๆ แต่ยิงไปที่ `/backend/...` ของตัวเอง
แล้ว Next.js เป็นคนส่งต่อให้ ตั้งค่าไว้ใน `next.config.mjs`:

```js
// next.config.mjs — หัวใจของการเชื่อม 2 ฝั่ง
async rewrites() {
  const backend = process.env.BACKEND_PROXY_URL ?? "http://localhost:8000"
  const media   = process.env.MEDIA_PROXY_URL   ?? "http://localhost:8001"
  return [
    { source: "/backend/:path*", destination: `${backend}/:path*` },  // API
    { source: "/media/:path*",   destination: `${media}/:path*` },    // รูปจากกล้อง
  ]
}
```

ข้อดีของการทำแบบนี้:

1. เบราว์เซอร์เห็นแค่โดเมนเดียว จึงไม่ติดปัญหา CORS
2. ไม่ต้องเปิดพอร์ต 8000 ออกสู่อินเทอร์เน็ต — บนเครื่องจริง FastAPI ผูกอยู่กับ `127.0.0.1:8000`
   เท่านั้น คนนอกยิงตรงไม่ได้เลย
3. เปลี่ยนที่อยู่ backend ได้โดยไม่ต้องแก้โค้ดหน้าเว็บสักบรรทัด

## 🔴 กับดักข้อแรกที่ทุกคนเจอ

ค่า `BACKEND_PROXY_URL` และ `MEDIA_PROXY_URL` ถูกอ่าน **ตอน build** ไม่ใช่ตอนรัน

ถ้าคุณไปแก้ค่าพวกนี้ใน `docker-compose.yml` ช่อง `environment:` เฉย ๆ **จะไม่มีผลอะไรเลย**
ต้องแก้ที่ `args:` ของส่วน `build:` แล้ว build image ใหม่ (รายละเอียดในบทที่ 13)

เหตุผล: Next.js เอาค่าเหล่านี้ไปฝังลงในผลลัพธ์การ build ตั้งแต่ตอนสร้าง image
ค่าที่ใส่ตอนรัน container จึงมาไม่ทัน

## สภาพจริงบนเซิร์ฟเวอร์ตอนนี้

```
$ docker compose ps
NAME                IMAGE             SERVICE    STATUS       PORTS
wimarc-backend-1    wimarc-backend    backend    Up 3 days    127.0.0.1:8000->8000/tcp
wimarc-frontend-1   wimarc-frontend   frontend   Up 3 days    127.0.0.1:3000->3000/tcp
```

- ทั้ง 2 container ตั้ง `restart: unless-stopped` — เครื่อง reboot แล้วขึ้นเองอัตโนมัติ
- ทั้ง 2 container รันด้วยผู้ใช้ที่ไม่ใช่ root (ปิดช่องโหว่ตามผลสแกนความปลอดภัย)
- PostgreSQL **ไม่ได้อยู่ใน Docker** — รันบนเครื่องโดยตรง container ต่อผ่าน `host.docker.internal`
