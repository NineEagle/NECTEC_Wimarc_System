## กฎข้อ 1 — เริ่มงานทุกครั้ง ต้องอ่าน notes ก่อน

```
notes/DEPLOYMENT_NOTES.md   ← ทุก feature/config ที่ deploy แล้ว
notes/BUGS.md               ← bug ที่เคยพบและแก้แล้ว
notes/SECURITY.md           ← ช่องโหว่และการปิดช่องโหว่
notes/IDEAS.md              ← ไอเดียและแผนที่ยังไม่ได้ทำ
```

เหตุผล: หลายอย่างในระบบนี้ "ดูเหมือนเขียนแปลก ๆ" แต่มีเหตุผลอยู่ในบันทึก
เช่น การ JOIN `sensor_1min` เพื่อเอาความกดอากาศ หรือการที่ Guest ต้องขอพิกัด
ถ้าไม่อ่านก่อนแล้วไป "แก้ให้ดีขึ้น" มักจะทำของเดิมพังโดยไม่รู้ตัว

| ประเภทงาน | จดที่ |

## กฎข้อ 4 — กติกาการเขียนบันทึก

- **ห้าม** ลบหรือเขียนทับเนื้อหาเดิม
- **ห้าม** จัดเรียงหรือปรับโครงสร้างหัวข้อเดิม
- **เสมอ** เพิ่มต่อท้ายไฟล์
- **เสมอ** จดหลังงานเสร็จสมบูรณ์เท่านั้น ไม่ใช่ระหว่างทำ
- **เสมอ** ใส่เลข commit ถ้ามีการ commit
- นับเลขลำดับต่อจากเลขสุดท้ายในไฟล์นั้น (ดูด้วย `grep -c '^### ' notes/BUGS.md`)

> **ทำไมห้ามแก้ของเดิม:** เพราะบันทึกคือประวัติศาสตร์ ไม่ใช่เอกสารสรุปสถานะปัจจุบัน
> ถ้าเรื่องเก่าไม่จริงแล้ว ให้เขียนรายการใหม่ต่อท้ายว่า "อัปเดตสถานะข้อ N: ..."

## การใช้ git ในโปรเจกต์นี้

### รูปแบบข้อความ commit

ใช้ Conventional Commits เป็นภาษาอังกฤษ ตัวพิมพ์เล็ก ขึ้นต้นด้วยคำกริยา

```
feat(harvest): add harvest log page
fix(map): re-centre the popup after its readings load
docs(notes): log the popup centring bug (BUGS 27)
fix(security): clear all dependency CVEs, run containers non-root
refactor(config): split the settings page into sections
```

| คำนำหน้า | ใช้เมื่อ |
|---|---|
| `feat` | ฟีเจอร์ใหม่ |
| `fix` | แก้บั๊ก |
| `docs` | เอกสาร/บันทึก |
| `refactor` | จัดโค้ดใหม่โดยพฤติกรรมเหมือนเดิม |
| `chore` | งานจิปาถะ เช่นอัปเดตไลบรารี |

ในวงเล็บใส่ขอบเขต เช่น `(map)`, `(faults)`, `(notes)`, `(security)`

### จังหวะการ commit ที่ทีมนี้ใช้

จาก `git log` จะเห็นว่าเขาแยกเป็น 2 commit เสมอ:

```
c747daf feat: hardware fault log — บันทึกอุปกรณ์เสียรายสถานี (Admin only)
ee77b6d docs(notes): log the hardware fault log feature (DEPLOYMENT 80)
```

commit แรกคือโค้ด commit ที่สองคือบันทึกที่อ้างถึงเลข commit แรก
ทำแบบนี้แล้วเลข commit ในบันทึกจะชี้ไปที่การเปลี่ยนแปลงจริงเสมอ

### คำสั่งที่ใช้ประจำ

```bash
git status                     # ดูว่าแก้อะไรค้างอยู่
git diff                       # ดูรายละเอียดสิ่งที่แก้
git add -A                     # เตรียม commit ทั้งหมด
git commit -m "feat(x): ..."   # บันทึก
git log --oneline -10          # ดูประวัติล่าสุด
git show <hash>                # ดูว่า commit นั้นแก้อะไรบ้าง
git revert <hash>              # ถอนการแก้ (เก็บประวัติไว้)
git push origin main           # ส่งขึ้น GitHub
```

- สาขาหลักคือ `main` และทีมนี้ทำงานบน `main` โดยตรง
- remote ชื่อ `origin` คือ `NineEagle/NECTEC_Wimarc_System` (ตัวที่ใช้จริง)
- remote ชื่อ `old-origin` เป็นของเก่า ไม่ต้องยุ่ง

### 🔴 สิ่งที่ห้าม commit เด็ดขาด

| ห้าม | เพราะ |
|---|---|
| `.env`, `backend/.env` | มีรหัสลับจริง (ถูกกันไว้ใน `.gitignore` แล้ว) |
| ไฟล์ PDF ใน `notes/` | ไฟล์ใหญ่ ลบออกจากประวัติ git ไม่ได้ถ้าไม่เขียนประวัติใหม่ |
| `node_modules/`, `.next/` | สร้างใหม่ได้เสมอ และใหญ่มาก |
| รหัสผ่าน คีย์ token ในโค้ดหรือคอมเมนต์ | หลุดแล้วต้องเปลี่ยนค่าใหม่ทั้งระบบ |

ถ้าเผลอ commit ความลับไปแล้ว **การลบใน commit ถัดไปไม่พอ** ต้องถือว่าค่านั้นหลุดแล้ว
และเปลี่ยนค่าใหม่ทันที
